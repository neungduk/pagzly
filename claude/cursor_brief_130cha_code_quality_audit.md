## 0. 배경 — 왜 지금 이걸 하는가

121~129차를 빠르게 연속 진행하면서 `[124cha]`, `[125cha]`, `[126cha]`, `[128cha]`, `[129cha]` 같은 라운드 번호 태그 `console.log`가 프로덕션 코드 곳곳에 누적됐습니다. 127차 검증 때 실제 서버 로그(`review/127cha-server.log`)를 직접 열어봤는데, 같은 흐름 안에 라운드 태그가 다른 로그 여러 개가 섞여 있어서 가독성이 떨어지는 걸 확인했습니다.

**중요 — 지우면 안 되는 것**: 이 라운드 태그 로그들은 지금까지 제가(Claude) 매 라운드 완료 리포트를 검증할 때 실제 증거로 써온 것들입니다(예: `[125cha][photo-pipeline]`, `[126cha][draft]` 로그가 실제로 찍히는지 확인하는 방식으로 126~129차를 검증했음). **이번 라운드는 이 감사(audit) 트레일 가치를 없애면 안 됩니다.** 목표는 "전부 삭제"가 아니라 "중복 제거 + 태그 정확도 확인 + 반복 로그 요약 추가"입니다.

## 1. 할 것

### A. 전체 인벤토리 먼저 (변경 전)

`lib/`, `app/`, `components/` 전체에서 `console.log`/`console.warn`에 `\[\d+cha\]` 패턴이 포함된 줄을 전부 grep해서 원문 그대로 리포트에 첨부. **이 목록을 먼저 만들고 나서** 아래 B~D를 진행 — 사후에 "뭘 지웠는지" 대조할 기준선이 필요합니다.

### B. 진짜 중복만 제거

같은 실행 흐름에서 **거의 동일한 정보를 두 번 찍는** 경우만 하나로 합칩니다. 예시로 확인한 것: `lib/photo-pipeline-client.ts`의 `[photo-pipeline] uploaded=X enhanced=Y passthrough=Z finalUnique=W` 로그와 바로 근처의 `[125cha][photo-pipeline] ...` 로그가 겹치는 정보를 담고 있는지 확인하고, 겹치면 라운드 태그 없는 쪽으로 통합(라운드 태그 로그의 필드를 흡수). **애매하면 합치지 말고 그대로 두기** — 확신 없는 통합보다 현행 유지가 안전합니다.

### C. 태그 정확도 감사 (내용은 그대로, 태그만 점검)

라운드 태그가 붙은 로그 중, **그 로그가 설명하는 동작이 이후 라운드에서 실제로 바뀌었는데 태그는 옛날 그대로인 경우**를 찾아서 리포트에만 남겨주세요(태그를 최신 라운드 번호로 바꾸는 것도 괜찮지만, 이력 추적용이니 지우지는 말 것). 예: `applyIngredientCircleVisual`의 로그가 129차에서 `spec_table` → `${insertBefore}`(동적)로 바뀐 것처럼, 문구가 실제 동작과 어긋나지 않는지 확인.

### D. 반복 로그 요약 추가 (삭제 아니고 추가)

127차 로그에서 직접 확인한 패턴: `[cost] sharpenCutout: clarity-upscaler ON (TEST_MODE=false): $0.0160`이 이미지 개수만큼 **동일한 줄로 반복** 찍힙니다(회당 로그는 유지하되, 파이프라인 끝에 `[cost] sharpenCutout total: N회 $X.XX` 같은 집계 한 줄을 **추가**하면 로그 스캔이 훨씬 쉬워집니다). `enhanceProductImage rembg`, `claude/productRegionDetect` 등 반복되는 다른 per-image 비용 로그도 같은 방식으로 파이프라인 종료 시점에 집계 한 줄씩 추가. 기존 개별 로그는 **삭제하지 않음**.

### E. 데드코드 스윕 (별도, 낮은 리스크)

129차에서 `applyIngredientCirclePair`(`@deprecated` 별칭, 실사용 0건)를 찾아 삭제했습니다. 같은 방식으로 코드베이스 전체에서 `@deprecated` 주석이 붙은 export를 전부 찾아서, 각각 실제 호출부가 있는지 grep으로 확인 후 **호출부 0건인 것만** 삭제 후보로 리포트. 호출부가 하나라도 있으면 그대로 둡니다(이번 라운드에서 억지로 마이그레이션하지 않음).

## 2. 검증

1. A의 grep 결과(변경 전 전체 인벤토리) 원문 첨부.
2. B~D 적용 후 같은 grep을 다시 돌려서 diff — 뭐가 합쳐졌고 뭐가 추가됐는지 원문 대조.
3. 기존 QA 스모크(69차/105차/124차/128차/129차 중 아직 재사용 가능한 것들) 재실행해서 **로그 정리가 실제 동작에 영향을 주지 않았는지** 확인 — 특히 128~129차의 combo 발동 여부가 로그 정리 후에도 그대로인지.
4. `tsc --noEmit` 0.
5. `git diff --stat` — 로직 파일(예: `lifestyle-product-composite.ts`, `apply-ingredient-circle-pair.ts`)에 **로그 줄 외의 변경이 없는지** 직접 diff로 확인 가능하게 첨부.
