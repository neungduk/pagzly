# 139차 — 다중 카테고리 회귀 QA (130~138차 누적 기능 통합 확인, 신규 유료 API 0)

생성: 2026-09-08

## 배경

130차부터 138차까지 아홉 라운드가 이어지면서 각 라운드는 자기 범위만 좁게 검증했습니다(정상적인
방식이었고 계속 유지할 겁니다). 그런데 그 사이 리포트에 **반복해서** 등장한 문장이 있습니다:

> "`DetailSectionRenderer.tsx` / `detail-preview` / `result/page`의 대형 diff는 131~136(또는
> 137) 미커밋 누적입니다."

즉 여러 라운드의 변경이 한 파일에 계속 쌓여왔는데, **그 누적된 상태를 카테고리 전체를 가로질러
한 번에 훑어본 적이 최근에 없습니다.** 마지막 전(全)카테고리 스크린샷 QA는 58차(8/28,
`58cha-preview-*.png` 6개 카테고리)였고, 그 이후로도 134/135/137/138차가 각각 편집 패널·리뷰
배지·축 비교·프레임워크 라벨을 추가했지만 전부 단일 케이스(주로 화장품, 리뷰 없음 또는 리뷰
있음 중 하나)로만 확인됐습니다.

이번 라운드는 **새 기능을 만들지 않습니다.** 지금까지 쌓인 것들이 카테고리 5종 전체에서 실제로
깨진 데 없이 잘 작동하는지 눈으로 확인하는 회귀 QA입니다.

## 목표

`TEST_MODE=true`로 아래 5개 카테고리 각각 1건씩 생성하세요(신규 유료 API 호출 없음, 기존
스모크 스크립트 패턴 재사용):

1. 화장품/뷰티 — **리뷰 파일 포함**(fixture, 135/137차 손검산에 쓴 것 재사용 가능)
2. 화장품/뷰티 또는 다른 카테고리 1건 — **리뷰 파일 없음** (135/137차 기능이 조건부로 생략되는지 확인용)
3. 패션/의류 — 가능하면 `color_variation` 섹션이 나오는 입력으로
4. 식품
5. 전자/가전 — 가능하면 `certifications` 입력값 포함(KC 인증 노출 확인용)
6. 생활/리빙

(화장품이 두 케이스라 총 6건. 시간이 부족하면 3~6은 최소 1건씩만이라도 좋습니다 — 카테고리
5종을 전부 한 번씩은 반드시 포함하세요.)

## 카테고리별로 확인할 것 (육안 체크리스트)

각 케이스마다 전체 스크롤 스크린샷(섹션 전부 보이게, 여러 장으로 나눠도 됨)을 찍고 아래를
확인하세요:

1. **135/137차 조건부 로직**: 리뷰 파일이 없는 케이스에서 `review_highlight`/`comparison_chart`
   (매칭형)가 실제로 생성되지 않는지. 리뷰 파일이 있는 케이스(1번)에서는 매칭 배지(`N건 언급`)와
   축 비교 차트(있다면)가 정상적으로 뜨는지.
2. **138차 프레임워크 라벨**: 판매자 에디터의 섹션 목록 사이드바에서, `canvas` 섹션을 제외한
   모든 섹션에 라벨 배지가 붙어 있는지. 카테고리마다 섹션 구성이 달라지므로, 매핑표에 없는
   새로운 섹션 타입이 튀어나오진 않는지(그럴 리는 없지만 확인 차원).
3. **134차 편집 패널**: `직접 편집` 진입 시 사이드바·`SectionPatchChat`·`DetailToolsAccordion`이
   카테고리 무관하게 깨지지 않는지(레이아웃 붕괴, 톤 이탈 없는지).
4. **48차 색상 스와치**: `color_variation` 섹션이 있는 케이스에서 스와치 클릭 시 이미지가
   실제로 바뀌는지(CSS-only 라디오 트릭, export HTML 기준으로도 확인).
5. **전자제품 KC 인증**: `certifications` 입력값이 `spec_table`에 "KC 인증" 행으로 정상
   노출되는지, 입력 없는 다른 카테고리에서는 그 행 자체가 생략되는지.
6. **옛 이미지 합성 버그 재발 여부**: 28차에서 진단했던 "유령 사각형"(반투명 회색 사각형이
   상품 위에 겹쳐 보이는 것) 같은 합성 아티팩트가 어느 카테고리에서든 재발하지 않았는지 육안
   확인.

## 검증

- 카테고리별 스크린샷 세트를 `review/qa-screenshots/139cha-{category}-full.png`(또는 섹션별로
  나눠 `-1`, `-2`...)로 저장.
- `review/139cha-report.md`에 **표 형식**으로: 카테고리 | 확인 항목 6개 | 결과(정상/이슈) | 비고.
- 이슈를 하나라도 발견하면 **이번 라운드에서 바로 고치지 마세요** — 원인 추정과 재현 조건만
  적어서 리포트에 남기고, 다음 라운드에 별도 브리프로 쪼개서 처리합니다(28차 선례와 동일한
  "진단과 수정 라운드 분리" 원칙).
- `npx tsc --noEmit` 1회(이미 여러 라운드에서 클린 확인됐으니 최종 확인용).
- 신규 유료 API 호출 0건(TEST_MODE만 사용) — 실제로 0인지 로그로 확인.

## 하지 않는 것
