# 219차 — 실제 생성물 재열람 + 후커블/디자이너 벤치마크 재대조 (무료)

생성: 2026-09-17 · 유료 API 0건 · 신규 크롤링 0건 (기존 자료만 재사용)

## 배경

"후커블과 디자이너가 만든 수준" 장기 과제(63~217차 다수)의 다음 한 걸음으로, 사용자가
선택한 방식(**"실제 생성물 직접 열람 + 재벤치마크 (무료)"**)에 따라 이미 만들어진
`review/181cha-live/{beauty,electronics,fashion,food,living,pet}/03-result-full.png`
6개 카테고리 전체 페이지 스크린샷(각 1280×17,000~19,500px, Playwright 데스크톱
뷰포트 1280×900 풀페이지 캡처)을 처음부터 끝까지 직접 다시 열람했습니다. 새 크롤링·
새 세션 생성 없이 기존 자료만 사용했습니다.

## 방법

각 스크린샷을 3등분해 19장으로 나눠 직접 눈으로 검토(158/181/208차 4축 방법론:
레이아웃 / 타이포·여백 / 이미지 합성 자연스러움 / 정보 위계). 의심 지점은 원본
PNG에서 해당 좌표를 다시 정밀 크롭해 재확인하고, 렌더링된 문구가 실제로 잘렸는지
아니면 슬라이스 경계 때문에 그렇게 보이는 것뿐인지는 반드시 `review/181cha-live/
{cat}/session.json`의 `generated.sections`에서 **원본 heading/body 원문**을 직접
대조해 확정했습니다(추측 금지 원칙 준수).

## 발견 — 버그 2건 (코드만으로 수정 가능, 유료 API 불필요)

### 버그 A — `image_text` 섹션 좁은 2단 레이아웃에서 헤드라인·본문이 "···"로 잘림

**증거 (session.json 원문 vs 렌더링 결과, 2개 카테고리에서 독립적으로 재현)**

| 카테고리 | 섹션 slot | 원문 heading | 렌더링 결과 | 원문 body(끝부분) | 렌더링 결과 |
|---|---|---|---|---|---|
| electronics | `design_detail` | "방 안에 놓이는 디자인" | **"방\n안에···"** (뒷부분 소실) | "...22×38×22cm 크기라 협탁이나 책상 한쪽에 놓입니다." | **"...협탁이나···"** (뒷부분 소실) |
| pet | `packaging_design` | "2kg 한 봉 포장" | **"2kg 한\n봉···"** (뒷부분 소실) | (본문은 이번엔 안 잘림) | — |

두 예시 모두 원문이 특별히 길지 않습니다(헤드라인 7~8자, 본문 1~2문장). 그런데도
잘린다는 것은 "AI가 유난히 긴 카피를 생성했을 때만 발동하는 안전장치"가 아니라,
**정상적인 카피 길이에서도 상시 재현되는 레이아웃 버그**라는 뜻입니다.

**원인 (코드 확인 완료, `components/DetailSectionRenderer.tsx`)**

- 이 레이아웃은 "FEATURE" 킥커 + 이미지/텍스트 2단 그리드(`case "image_text"`,
  1866~1936행 부근)이며, `lib/detail-visual-rhythm.ts`의 `resolveSplitColumnRatio()`
  (156차 도입)가 POINT 순번에 따라 텍스트 컬럼을 50%→60%→**40%**로 3주기 순환시킵니다.
- 헤드라인엔 `HEADLINE_CLAMP`(`line-clamp-2`, 184행), 본문엔 `line-clamp-5`(1935행)가
  걸려 있고, 헤드라인 폰트는 `TYPO.sectionTitle`(2rem→`sm:`2.75rem, 224~225행)로 매우
  큽니다.
- 캡처는 데스크톱 뷰포트(1280×900, `scripts/181cha-live-generate.ts` 262행)지만,
  실제로 보이는 것은 에디터 중앙의 **좁은 모바일 미리보기 프레임**(고정 폭 `<div>`)
  입니다. Tailwind의 `sm:` 반응형 클래스는 프레임 폭이 아니라 **브라우저 뷰포트
  폭**(1280px, ≥640px)을 기준으로 평가되므로 `sm:grid-cols-[2fr_3fr]` 같은 2단
  그리드가 그대로 적용되고, 그 결과 좁은 모바일 프레임 안에서 텍스트 컬럼이
  40%만 차지하게 됩니다 — 2.75rem짜리 헤드라인이 실제로는 3줄이 필요한데
  `line-clamp-2`가 2줄에서 잘라버리는 것입니다. 156차 커밋 주석(52~59행)에서도 이미
  "텍스트 컬럼이 너무 좁아지면 line-clamp 본문이 읽기 힘들어진다"는 위험을
  인지하고 40%를 하한으로 뒀지만, 실측 결과 40%로도 부족했습니다.
- **참고**: 정적 export(`lib/export-detail-html.ts`, 433행 `case "image_text"`)는
  line-clamp를 전혀 쓰지 않아 이 버그의 영향을 받지 않습니다 — 즉 **최종 다운로드
  상세페이지(구매자가 보는 것)는 멀쩡**하고, **판매자가 에디터에서 미리보기할 때만**
  헤드라인/본문이 깨져 보입니다. 그래도 판매자가 "이 도구가 내 카피를 망가뜨렸다"고
  오해해 신뢰를 잃을 수 있는 실사용 버그이므로 수정 대상입니다.

### 버그 B — `highlight_box` 카드의 초대형 키워드가 영문/숫자 혼합 값일 때 옆 카드로 흘러넘침

**증거**

fashion `highlight_box` 섹션(§ "세 가지 포인트") 카드 2의 원문 title은
`"210g/yd"`(session.json 원문 확인 완료)입니다. 렌더링 결과 이 문자열 전체가
초대형 키워드(`clamp(2.25rem,11vw,4.25rem)`, `text-transform:uppercase`)로
확대 표시되면서 카드 폭을 넘어 **옆 카드(포인트 3 "수축")의 텍스트 위에 겹쳐
표시**됩니다. 같은 섹션의 카드 1("코튼 100%")·카드 3("수축 2%↓")은 첫 토큰이
순수 한글 2글자("코튼", "수축")라 정상 렌더링됩니다.

**원인 (코드 확인 완료, `lib/detail-visual-enhancements.ts` 16~38행)**

`parseMegaKeywordHeading()`이 제목의 **첫 공백 구분 토큰을 길이(2~10자)만 보고**
무조건 초대형 키워드로 승격시킵니다. "210g/yd"는 라틴 문자로 시작하지 않아
라틴 전용 분기(24~30행)는 건너뛰고, 일반 분기(32~35행)에서 길이 7자(2~10자 범위)
조건을 통과해 문자열 전체가 그대로 키워드가 됩니다. 문제는 렌더링 쪽
(`TYPO.keywordDisplay`, `DetailSectionRenderer.tsx` 226~227행 / export HTML
`FONT_SIZE.keywordClamp`·`keywordClampCard`, `lib/export-detail-html.ts` 231·253·262행)
**어디에도 `overflow-wrap`/`word-break` 보호가 없다**는 점입니다. 한글 단어는
브라우저가 음절 단위로 자동 줄바꿈해 주지만, "210g/yd" 같은 라틴+숫자+기호
혼합 문자열은 공백이 없어 줄바꿈 지점이 없고, 그대로 카드 밖으로 흘러넘칩니다.
**이 버그는 라이브 에디터 미리보기뿐 아니라 정적 export HTML(`export-detail-html.ts`
255행 `display:grid;grid-template-columns:repeat(3,1fr)` 카드 그리드)에도 동일하게
존재**하므로, 실제로 판매자가 다운로드해 마켓에 올리는 최종 상세페이지에서도 발생할
수 있는 **구매자 대면 버그**입니다 — 버그 A보다 우선순위가 높습니다.

## 발견 — 기록만 하고 이번엔 손대지 않는 항목 (카피 품질/취향, 코드 버그 아님)

### living `highlight_box` 카드 2 — "단당 80kg" (원문 그대로, session.json 확인)

렌더링은 코드가 의도한 대로(첫 토큰 "단당"을 정상적으로 키워드 처리) 동작했지만,
**"단당"이라는 원문 자체가 자연스러운 한국어 단어가 아닙니다** — "1단당"(선반 한
단마다)에서 앞의 수사 "1"이 빠진 것으로 보이는 카피입니다. 이는 렌더링/CSS 버그가
아니라 **카피 생성(AI 프롬프트) 단계의 완결성 문제**이며, 고치려면
`highlight_box.cards[].title`을 생성하는 프롬프트/로직을 건드려야 합니다. 이번
라운드는 "코드만으로, 유닛 테스트로 검증 가능한" 범위로 스코프를 좁혔으므로
**이번엔 조사만 하고 백로그에 후보로만 기록**합니다(158/159/183/206차 등과 동일한
절제 원칙).

  198차의 누적 개선이 반영된 상태로 판단).
