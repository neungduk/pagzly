## 하드 가드레일 (반복)

Replicate/Claude/DeepSeek 등 생성 API 호출 절대 금지. `/api/generate` 실행 금지. 이번
라운드는 **새 이미지를 만들지 않습니다** — 이미 `review/181cha-live/{cat}/session.json`에
있는 이미지 URL이 스크린샷에 실제로 로딩되도록 QA 툴링만 고치고, 로딩된 상태에서 197차가
못 끝낸 검증을 마저 합니다.

## 배경 — 197차 스크린샷을 직접 열어보니 사진이 전부 깨져 있었습니다

197차 보고서는 "사진이 로드된 샘플에서 상단 톤이 브랜드색으로 오염되지 않음"이라고 했지만,
제가 스크린샷 8장(에디토리얼 6장 중 6장 확인, 배너 2장)을 직접 열어본 결과 **전부 사진이
안 뜨고 깨진 이미지 아이콘 + alt 텍스트만 보였습니다**:

- `197cha-editorial-{beauty,electronics,living,pet,food,fashion}-*.png` 6장 전부: 이미지
  자리에 브라우저 기본 "깨진 이미지" 아이콘 + alt 텍스트만 보이고, 사진 자체는 안 보임.
  그 아래 중립 스크림(회색 그라데이션)과 흰 글씨 캡션은 정상적으로 보임 — 즉 **스크림
  자체의 색상은 문제없어 보이지만, 정작 검증하려던 "스크림이 실제 사진과 부딪히는가"라는
  질문은 사진이 없어서 확인이 안 된 상태**입니다.
- `197cha-banner-{food,electronics}.png` 2장도 마찬가지로 이미지가 안 뜨고, export의
  `deepFill` 솔리드 배경(브랜드 색 단색)만 보임 — 이건 export 설계상 이미지 실패 시
  자연스러운 폴백이라 이 2장만으로는 큰 문제 아니지만, 역시 실사진으로는 재확인이 안 된
  상태입니다.

**즉 197차의 핵심 결론("사진 색과 안 부딪힌다")은 아직 증명되지 않았습니다** — 대신 "사진이
없을 때 스크림 자체 색상은 이상 없다"만 확인된 것입니다. 이미지 URL을 직접 열어보면
(`review/181cha-live/food/session.json`의 `imageUrls[0]`, 예:
`https://sblnthhayvrfkvaksest.supabase.co/storage/v1/object/public/images/...-enhanced.png`)
Supabase **public** 스토리지 URL이라 만료(presigned 링크처럼 시간 제한)될 이유는 없어
보입니다 — 그러니 원인은 (a) 실제로 해당 파일이 스토리지에서 삭제/이동됐거나, (b) 197차가
스크린샷을 찍은 툴/환경이 외부 네트워크 이미지 로딩을 못 했거나(로컬 파일 렌더링, 네트워크
차단 등), (c) export HTML을 만들 때 쓴 `imageUrls` 값 자체가 어긋났거나 — 이 중 하나입니다.
195/196차 때는 같은 방식(export 재렌더링)으로 찍은 food/fashion 스크린샷에 실제 사진이
정상적으로 보였으니, **197차 스크린샷 촬영 사이에 뭔가 달라졌을 가능성**이 높습니다.

## 작업

### A. 원인 진단 (최우선)

1. `review/181cha-live/food/session.json`의 `imageUrls[0]`을 브라우저나 `curl -I`로 직접
   열어 실제로 200이 오는지, 404/만료/다른 에러인지 확인하세요.
2. 200이면: 197차가 스크린샷을 찍은 방법(어떤 스크립트/툴, 헤드리스 브라우저인지, 네트워크
   접근 권한이 있었는지)을 확인해 왜 이미지가 안 실렸는지 찾으세요. 195/196차 때와 197차
   때 스크린샷 촬영 방식이 달랐다면 그 차이가 원인일 가능성이 큽니다.
3. 404/삭제됐으면: **재생성하지 말고** 그 사실만 보고서에 남기고, 이미지가 살아있는 다른
   카테고리/세션으로 대체해서 검증하세요(예: 같은 세션의 다른 `imageIndex`, 또는
   `imagePaths`가 로컬에 캐시된 파일이 있는지 확인 — 있으면 그걸로 대체).

### B. 원인 해결 후 — 197차가 못 끝낸 검증 다시

트랙 A(에디토리얼 풀블리드) 6개 섹션 전부, 사진이 실제로 보이는 상태로 다시 스크린샷:

- food `serving_suggestion`, fashion `coordination`/`seasonal_styling`, beauty
  `customer_scenario`, electronics `usage_scenario`/`install_scenario`, living
  `usage_scenario`, pet `usage_scenario`

각 스크린샷에서 사진 원래 톤이 위쪽 40%+ 구간에서 그대로 보이는지, 브랜드색으로 오염되지
않는지 이번엔 실제로 눈으로 확인하세요. 오염되는 카테고리가 있으면
`getEditorialBleedScrim()`(196차, `DetailSectionRenderer.tsx`)의 정지점/불투명도를 그
카테고리 근거로 미세 조정하세요.

`illustration_banner`(트랙 B)도 같은 김에 사진이 실제로 보이는 상태로 food/electronics
2장만 다시 찍어서, 197차의 "이상 없음" 판단이 사진 로딩 상태에서도 유지되는지 한 번 더
확인하세요.

## 검증

1. `npx tsc --noEmit` — 0.
2. A에서 찾은 원인을 보고서에 명시(200/404, 툴링 문제 등).
3. B의 스크린샷 전부 **실제 사진이 보이는 상태**로 재촬영 — 이번엔 스크린샷 파일을 열어
   사진이 진짜 로딩됐는지 직접 확인 후 제출하세요(197차처럼 "확인함"이라고만 적고 실제로는
   깨진 이미지였던 일 반복 금지).
4. 이미지 생성 API 호출 0회 확인.

## 하지 않는 것

- 생성 API 호출 전부 금지(0회) — 이미지가 깨져 있어도 절대 새로 생성하지 않습니다. 원인이
  "파일 삭제됨"으로 확인되면 대체 이미지(같은 세션 내 다른 인덱스)로 검증하거나, 대체할
  게 없으면 "이번 라운드는 검증 보류"로 정직하게 보고하세요.
- 195/196/197차가 만든 스크림 로직·구조 자체는 이번엔 수정하지 않음(진단 결과 실제로
  오염이 재현될 때만 정지점/불투명도 미세 조정) — 이번 라운드의 본질은 "검증 방법을
  고치는 것"입니다.
