# 227차 — "Before/After 효과 비교" 입력 기능 설계 검토 (코드 변경 없음, 결정 대기)

생성: 2026-09-18 · 유료 API 0건 · **이 문서는 브리프가 아니라 설계 검토입니다 — 사용자 결정 후 브리프 작성**

## 0. 배경

226차 쿠팡 반려동물 사료 크롤링에서 발견한 "Before/After 실사진 비교 모듈"(눈물자국 개선 전/후
사진 + 구매자 리뷰 인용, 반복 2세트)을 Pagzly에 들일지 검토합니다. 226차 결론대로 이건 코드
버그가 아니라 **입력 기근**(사용자가 이런 사진을 올릴 슬롯 자체가 없음) — 입력 슬롯을 새로
만들지 여부가 이번 검토의 핵심 질문입니다.

## 1. 가장 먼저 확인한 것 — 법적 리스크가 이 기능의 핵심 변수입니다

기존 코드(`lib/pet-compliance.ts`, `lib/cosmetics-compliance.ts`, `lib/food-compliance.ts`)를
다시 읽어보면, Pagzly가 이미 **정확히 이 3개 카테고리**(화장품/뷰티, 반려동물, 식품)에서 "효과·
효능을 확정적으로 주장"하는 표현을 서버가 강제로 순화하고 있습니다:

- 화장품: "제거", "재생", "미백 효과", "의학적으로 증명", "임상 실험" 등 금지 — 화장품법 광고 기준
- 반려동물: "질병 예방/치료", "완치", "약효" 등 금지 — 표시광고법·사료관리법 기준
- 식품: (`lib/food-compliance.ts`, 동일 계열)

**Before/After 사진 비교는 이 규제가 막으려는 것과 같은 종류의 주장을, 텍스트가 아니라 사진으로
하는 것**입니다. 오히려 사진은 regex로 순화가 불가능하다는 점에서 텍스트보다 리스크가 더
큽니다 — "눈물자국이 좋아졌어요" 같은 문구는 `sanitizeText()`로 걸러지지만, "눈물자국 있는 사진 →
없는 사진"을 나란히 놓는 것 자체가 실질적으로 같은 효능 주장이고 코드로 순화할 방법이 없습니다.
화장품법·건강기능식품법 실무에서 "전후 비교 사진"은 표시광고 심사에서 가장 흔히 적발되는 유형
중 하나이기도 합니다(임상적 근거 없는 사진 비교 = 효능 오인 소지).

**두 번째 리스크**: 사진의 진위. Pagzly의 반복된 원칙("입력되지 않은 통계·인증·후기 날조 금지")은
"AI가 지어내지 않는다"는 것이지 "판매자가 올린 사진이 진짜라는 걸 보증한다"는 게 아닙니다. 다른
업로드 사진도 마찬가지 한계가 있지만, Before/After는 태생적으로 "효과가 있었다"는 **주장**을
담은 사진이라 오남용(조명·각도를 다르게 찍어 과장) 유인이 다른 제품컷보다 훨씬 큽니다. Pagzly가
이런 사진을 업로드받아 그대로 발행하면, 사진의 진위·과장 여부와 무관하게 "효과를 증명하는
비교"라는 틀을 플랫폼이 제공하는 셈이 됩니다.

## 2. 코드 구조 확인 결과

- `lib/types/generate.ts`의 `ProductInput`/`DetailSection`을 전수 검색 — "before/after" 관련 필드
  0건. 기존 이미지 업로드는 `imageUrls`(배열) + `imageRoles`(역할 태그: hero/detail/lifestyle/
  package/other, `CreateProductForm.tsx` 839~919행)만 있고, "쌍(pair)"으로 묶어 올리는 UI는
  없음 — `circlePair`/`circleSolo`(image_text 레이아웃)가 그나마 가장 비슷하지만, 이건 **AI가
  섹션 콘텐츠로 생성하는** 것이지 사용자가 실사진 2장을 짝지어 올리는 것과는 다릅니다.
- `ReviewHighlightSection`(`lib/types/generate.ts:436`)은 "AI는 이 섹션을 생성하지 않는다,
  서버가 실데이터로 조립한다"는 전례가 이미 있음 — Before/After를 만든다면 같은 원칙(AI 비생성,
  사용자 입력 그대로 조립)을 따라야 함.
- `lib/section-templates.ts`의 카테고리별 슬롯 목록에 "효과 비교"류 슬롯은 없음 — 만들려면
  기존 6개 카테고리 템플릿에 슬롯을 추가하는 게 아니라, **입력이 있을 때만 나타나는 선택적
  add-on 섹션**으로 설계하는 게 기존 관례(`sellerTrustEvidence`처럼 "비어 있으면 섹션을 생성하지
  않음" 패턴, 147행 주석)에 맞습니다.

## 3. 설계안 (만든다면 이렇게) — 아직 결정 아님

1. **입력**: `CreateProductForm.tsx`에 기존 사진 업로드와 별개로 "효과 비교 사진(선택)" 블록을
   추가 — "전" 슬롯 1장 + "후" 슬롯 1장을 한 쌍으로, 여러 쌍 추가 가능(쿠팡 사례처럼 2쌍 이상).
   `ProductInput`에 `beforeAfterPairs?: { beforeUrl: string; afterUrl: string; caption?: string }[]`
   신설. 캡션은 사용자가 직접 짧게 타이핑(예: "2주 사용 후") — **AI가 캡션을 새로 짓지 않음**.
2. **섹션 타입**: `BeforeAfterSection`(`type: "before_after"`) 신규 — `pairs`를 그대로 받아
   Before/After 라벨 + 이미지 2장 + (있으면) 사용자 캡션만 렌더링. `ReviewHighlightSection`과
   동일하게 **서버 조립 전용, DeepSeek 생성 대상 아님**(AI가 프롬프트로 "효과"를 부풀려 쓸 여지
   원천 차단).
3. **고정 컴플라이언스 각주**: `INGREDIENT_HIGHLIGHT_COMPLIANCE_NOTE`(160차 선례)와 같은 방식으로,
   카테고리 불문 고정 문구를 항상 함께 노출 — 예: "*개인차가 있을 수 있으며, 사용 경험은 실제
   구매자가 제공한 사진입니다." AI가 생성하지 않는 고정 문자열이라 컴플라이언스 규칙과 무관하게
   항상 붙음.
4. **카테고리 게이팅 — 가장 중요한 결정 지점**:
   - **A안(보수적, 권장)**: 화장품/뷰티·반려동물·식품(이미 컴플라이언스 모듈이 있는 3개 카테고리,
     즉 "효과·효능" 표시가 법적으로 가장 민감한 카테고리)은 **이 섹션 자체를 제공하지 않음**.
     전자제품(청소 전/후, 정리함 전/후)·생활용품(수납/청소 전후)·패션(스타일링 전후)처럼 "의학적/
     효능적 주장으로 읽히지 않는" 카테고리에만 한정. 기존 컴플라이언스 게이팅 패턴(`isPetCategory`
     `isCosmeticsCategory` 등)과 정반대 방향(민감 카테고리를 제외)으로 동일한 사고방식을 적용.
   - **B안**: 전 카테고리 허용하되, 캡션 텍스트를 해당 카테고리의 기존 `sanitizeText()`에 통과시키고
     화장품/반려동물/식품엔 위 고정 각주를 더 강하게("의료적 효과를 의미하지 않습니다" 등) 명시.
     사진 자체의 리스크(§1)는 텍스트 필터로 줄일 수 없다는 한계는 남음.
   - **C안**: 이번엔 만들지 않음 — 226차에서 발견한 4개 패턴 중 나머지 3개(스타일·취향 차이)처럼
     후보로만 기록하고 종료.

## 4. 권장

**A안(보수적 카테고리 제한) 또는 C안(보류)을 권장합니다.** 이 기능은 "화면에 어떻게 보이는가"의
문제가 아니라 "무엇을 증명한다고 주장하는가"의 문제라, 코드 버그 수정이나 스타일 이식과는 리스크
성격이 다릅니다. 226차에서 발견된 실제 사례(쿠팡 반려동물 사료)가 정확히 A안이 배제하려는
카테고리(반려동물)라는 점도 고려할 부분 — 가장 매력적으로 보였던 실제 사례 자체가 A안 기준으로는
"만들어도 못 쓰는" 카테고리입니다.
