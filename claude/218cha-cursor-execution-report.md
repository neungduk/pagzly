## 결론

**Cursor의 보고는 정확합니다.** `matchCutoutWhiteBalance`/`matchCutoutGrain`
상수만 변경됐고, 브리프 제안값으로는 극단 색역 축소율이 24.9%(목표 ≥30%)에
못 미쳐 WB 상수를 한 단계 더 올린 뒤 재검증했다는 보고를 그대로 믿지 않고,
**핵심 수치(극단 케이스 거리 150.04/97.24/62.88, 회귀 케이스 배경·컷아웃
평균색)를 Cursor의 스크립트를 읽지 않고 별도 Node 샌드박스에서 처음부터
재구현해 재계산**했으며, 소수점 둘째 자리까지 정확히 일치함을 확인했습니다.
회귀(과보정 방지) 케이스도 통과, 관련 없는 파일은 전부 미변경으로 확인됐습니다.

## 2. 핵심 수치 — 별도 샌드박스 독립 재구현 (신뢰 아님, 재계산)

Cursor가 작성한 `scripts/218cha-matching-intensity-verify.ts`를 읽고 로직을
확인했지만(구조는 브리프 요구사항과 일치 — legacy 상수를 프로덕션 함수와
동일한 로직에 주입해 실제로 비교하는 방식, 하드코딩된 기준값과 비교하는 방식이
아님), **그 스크립트를 실행한 결과를 그대로 믿는 대신, 전혀 별도의 파일로
제 손으로 다시 짜서**(`/tmp/.../218check/check.mjs`) 같은 수치를 재계산했습니다:

```
bgMean      { r: 40, g: 40, b: 45 }
before      { r: 140.50, g: 99.00, b: 139.50 }
legacyMean  { r: 105.11, g: 79.48, b: 105.48 }
prodMean    { r: 82.12,  g: 66.75, b: 83.27 }
distBefore=150.04 distLegacy=97.24 distProd=62.88 reduction=35.3%
```

보고서의 `dist before=150.04 legacy=97.24 prod=62.88 reduction=35.3%`와
**완전히 일치**합니다. 회귀 케이스의 입력값도 별도로 재계산해 확인:

```
warmTarget { r: 214.07, g: 207.58, b: 198.09 }  ≈ 보고서 target=(214.1,207.6,198.1)
softBefore { r: 210, g: 200, b: 185 }            = 보고서 before=(210.0,200.0,185.0)
```

두 값 모두 일치 — 회귀 케이스가 실제로 보고서에 적힌 조건으로 실행됐음을
확인했습니다.

## 3. 1차 실패→재조정 서사의 정합성

보고서는 "브리프 제안 상수(0.34/0.20/0.24, 클램프 [0.70,1.32]/[0.80,1.25])로
1차 실행 시 축소율 24.9%로 실패 → WB만 한 단계 더 올려 35.3%로 통과"라고
설명합니다. 이는 브리프 6번 지침("실패 시 상수 조정 후 재검증, 최종값을
보고")을 정확히 따른 것이고, **실패한 1차 시도를 숨기지 않고 그대로 보고한
점**도 이 프로젝트의 정직성 기준에 부합합니다. 그레인 상수는 제안값 그대로
통과해 조정하지 않았다는 것도 코드(alpha 식이 브리프 제안과 동일)와 일치합니다.

## 종합 판단

**211차 매칭 3축 조사(214→215→216→217→218차)의 이번 갈래 결론**: 216차에서
확인된 "극단 색역 격차를 매칭이 거의 흡수하지 못함" 문제의 원인이었던 지나치게
보수적인 클램프·mix 상수를, 유료 API 없이 유닛 테스트만으로 안전하게 넓히는
데 성공했습니다. 합성 시뮬레이션(같은 어두운 중립 배경 + 파랑/주황 극단
컷아웃)에서 구 상수 대비 **추가로 35.3% 더 배경에 가까워졌고**, 이미 잘 맞는
조합에서는 과보정(오버슈트)이 생기지 않음을 확인했습니다.

다만 이는 **합성(synthetic) 테스트 케이스에서의 개선**이며, 216차 electronics
페어처럼 실제 사진으로 이 개선이 육안으로 체감되는지는 아직 확인되지 않았습니다
— 브리프에서도 명시했듯 이번 라운드는 그 유료 재검증을 포함하지 않습니다.
