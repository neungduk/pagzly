## A. PDF/사진 읽기 품질 (원인이 확인된 것부터)
### A-1. 세로로 긴 PDF/이미지를 통째로 줄여서 글자가 뭉개진다 (실제 파일로 확인된 원인)
재현 파일: 쇼핑몰 상세페이지 전체 캡처 PDF(FireShot), 1쪽, **595 x 5678pt**, 글자 레이어 없음, 내장 이미지 폭 1803px(218ppi).
현재 흐름(`lib/label-check/client-ocr-prepare.ts`): `getViewport({ scale: 1.5 })` → 893 x 8517px 캔버스 → `bitmapToTiles`가 `fitLongEdge508(…, OCR_LONG_EDGE_MAX_508=4000)`으로 **긴 변(세로 8517)을 4000에 맞춰 전체를 0.47배로 축소** → 폭이 약 420px이 된다. 본문 글자 높이가 3~5px이 되어 OCR이 엉뚱한 글자를 낸다. 세로로 긴 사진(상세페이지 이미지)도 같은 경로로 뭉개진다.
수정:
- **축소 기준을 "긴 변"이 아니라 "폭"으로.** 세로는 타일로 자르므로 제한할 필요가 없다. 폭 목표 `OCR_TARGET_WIDTH_518 = 1800`(상한 2400), 세로는 `computeVerticalTiles508`로 분할. `fitLongEdge508`은 가로로 긴 이미지(폭 > 높이)에만 적용하거나, 폭 기준 새 함수 `fitWidth518`을 만들어 `bitmapToTiles`에서 사용(구 함수는 남김).
- PDF 렌더 scale: `scale = clamp(OCR_TARGET_WIDTH_518 / pageWidthPt, 1.5, 5)`. 위 파일이면 약 3.0 → 1800 x 17,170px. 한 캔버스 픽셀 상한(예: 16MP, iOS Safari 고려)을 넘으므로 **페이지를 세로 구간별로 나눠 렌더**한다(pdfjs `viewport` + `transform`/offset으로 구간 캔버스에 그리기, 구간 높이 = 타일 높이 + 겹침). 한 번에 큰 캔버스를 만들지 말 것.
- 타일 수 상한: 1800 x 17,170 / 2400 ≈ 8타일로 상한 20 이내. 상한을 넘는 경우 거절하지 말고 폭 목표를 1800→1500→1200으로 낮춰 재계산하고, 1200에서도 넘으면 앞에서부터 상한까지만 읽고 "문서가 길어 앞부분 N%만 읽었어요"(기존 508 '일부읽음' 흐름 재사용).
- JPEG 품질 0.85 → 0.92(타일 3MB 상한 안에서, 기존 shrink 유지).
- 사진 원본 폭이 1000px 미만이면 OCR 확인 카드에 "사진이 작아 글자가 흐릴 수 있어요. 더 크게 찍거나 PDF를 올려 주세요"(차단하지 않음).
- CLOVA는 요청당 타일 6개(`OCR_MAX_TILES_PER_REQUEST_CLOVA_509`), 타임아웃 8초, 함수 30초 한도가 있다. 타일이 늘어도 기존 배치·병렬(`OCR_PARALLEL_508`) 로직으로 처리되는지 확인하고, 호출 수 증가가 월 한도 계산(`usage.ts`)에 맞게 집계되는지 테스트.
- 회귀 테스트: 595x5678pt 입력 시 결과 타일 폭 ≥ 1500px, 타일 수 ≤ 20, 어떤 캔버스도 16MP 초과 없음. 가로로 긴 입력·일반 A4·작은 라벨 판형 각각 1케이스.
- **참고**: 이 파일은 라벨이 아니라 상세페이지 캡처다. 상세페이지는 광고 문구 점검 대상이므로 읽기는 해야 하지만, 필수 표시사항(제조번호·사용기한 등)이 "없다"고 나오는 것은 당연하다. 읽은 글자에 쇼핑몰 UI 문구(장바구니, 리뷰, 배송, 결제 등)가 많으면 결과 상단에 "상세페이지로 보여요. 광고 문구 위주로 봐 주세요. 라벨 표시사항은 라벨 파일로 점검하세요" 안내를 띄우고 기본 모드를 '광고 문구만'으로 제안(자동 변경하지 말고 버튼 제공). 판정 로직 변경 금지.
### A-2. 글자 레이어가 있는 PDF는 OCR보다 텍스트를 우선
`client-extract-pdf.ts`의 텍스트 추출 결과가 충분하면(현재 기준 확인 후 보고서에 수치 기재) OCR로 가지 않는지 확인하고, 텍스트 레이어가 있는데도 OCR로 빠지는 경로가 있으면 고친다. 텍스트 레이어가 일부만 있는 PDF(일부 윤곽선 처리)는 "일부 글자가 그림으로 되어 있어 사진 읽기를 함께 썼어요" 안내.
### A-3. 신뢰도 낮은 글자 표시
CLOVA `inferConfidence`/Vision confidence가 이미 줄 단위로 계산된다. 
- OCR 확인 카드에서 **신뢰도 낮은 줄(평균 < 0.75)을 노란 배경**으로 표시하고 상단에 "노란 줄은 글자가 흐려 틀렸을 수 있어요. 고친 뒤 점검하세요"(색만으로 구분하지 말고 줄 앞에 "확인" 표식).
- 전체 평균이 0.6 미만이거나 한글/영문 비율이 비정상(특수문자·낱자 과다)이면 판정으로 넘어가기 전에 "글자를 제대로 읽지 못했어요" 상태로 두고 재촬영/PDF 안내(기존 508 "점검불가/일부읽음" 흐름 재사용, 새 상태 추가 금지). 임계값은 상수로 두고 테스트.
- textarea 편집은 유지하되 줄 표시는 textarea 위 미리보기 영역에서 한다(아래 B).
### A-4. 읽는 순서
단어 박스 좌표가 있으므로, 한 타일 안에서 **같은 줄(y 겹침 50% 이상) → x 오름차순**으로 정렬한 뒤 줄을 잇는지 확인하고, 2단 레이아웃에서 줄이 섞이는 경우(줄 사이 x 간격이 타일 폭의 12% 이상 벌어지면 다른 덩어리로 분리)를 처리한다. 목업 좌표 데이터로 테스트. 회전(세로) 글자는 이번 범위 아님(보고서에 한계로 기재).
### A-5. 진단용 수치(저장 없음)
결과 메타에 `ocrQuality: { avgConfidence, lowLineCount, lineCount, renderScale, tiles }`를 화면 전용으로 싣고(저장·로그에 원문 금지), 결과 화면 맨 아래 작은 글씨로 "읽기 품질: 보통(평균 0.82)" 수준만 표시.

## B. OCR "읽은 글자 확인" 카드가 스타일 없이 나온다 (사용자 지적)
517 화면에서 `OcrReviewCard`가 구 CSS 없이 렌더되어 textarea가 200px 폭, 버튼이 글자만 보인다. 517 문법으로 새로 만든다(`ui-517/OcrReview517.tsx`, 구 파일 유지):
- 무대(왼쪽 큰 패널) 안에 표시. 제목 "읽은 글자를 확인해 주세요", 한 줄 설명, 외부 OCR 전송 고지(기존 문구 유지).
- 2열: 왼쪽 올린 사진 썸네일(있을 때), 오른쪽 **전체 폭 textarea**(최소 높이 320px, 줄간격 1.8, 고정폭 아님) + 신뢰도 낮은 줄 안내(A-3).
- 버튼: 검정 알약 "이 글자로 점검"(주), 테두리 알약 "취소"(보조). 오른쪽 설정 패널의 점검 버튼은 이 단계에서 숨기거나 비활성(버튼 2개 혼동 방지).
- 푸터 링크 "샘플 결과 보기 · 문의"는 카드 밖 아래 유지.

## C. 펼친 결과 카드 본문을 시안대로
현재 검정 카드 안에 흰 상자 + "무엇이 문제인가요 / 라벨에서 확인한 내용 / 이렇게 넣어 보세요"가 세로로 쌓여 구 512 모습 그대로다. `review/design-517/result-v5.dc.html`의 펼침 영역대로:
- 한 줄 이유(why) → 2블록: wording = BEFORE(걸린 문장, 걸린 말 밑줄) / AFTER(대체 문구 + 복사), missing = "라벨에서"(찾지 못했어요) / "이렇게 넣어 보세요"(+복사), measure = 읽은 값 / 기준. 예시 없으면 두 번째 블록 없음. 취소선 금지.
- 검정 카드(고칠 것)에서는 블록 배경을 반투명 색(rgba(255,90,66,.16) / rgba(127,162,255,.18))으로, 흰 카드에서는 #F3F5FB / #EEF2FF. 안쪽 흰 상자 제거.
- 하단 한 줄: 기준(법령) 왼쪽, "고쳤어요" 오른쪽. "예시 문구입니다…" 고지는 예시가 있을 때만 작은 글씨.
- 512 분류 로직(`classifyFinding512`)과 데이터는 그대로, 표현 컴포넌트만 `FindingBody518`로 새로 만든다.

## D. 직접 확인 항목·번호
- 번호가 8 다음 20으로 건너뛴다(문제 없음이 접히면서). 번호는 **화면에 보이는 순서대로 다시 매기지 말고**, 고칠 것→확인할 것→직접 확인→문제 없음 순서로 처음부터 연속 번호가 되게 행 목록 생성 순서를 바꾼다(핀 번호와 일치 유지).
- 샘플에서 직접 확인 5개(표준 국문 성분명, 수출 전용, 개정안, 세트, 색조)가 그대로 나온다. 513의 게이팅이 샘플/붙여넣기 경로에도 적용되는지 확인하고, 옵션 미선택 시 "해당하지 않아 뺀 항목"으로 가야 할 것(수출 전용·세트·색조)이 직접 확인에 남는 원인을 고친다. 개정안은 "참고"로.
- 직접 확인 묶음도 문제 없음처럼 3개 초과 시 접는다.

## E. 판정 누락 확인 (조사 + 최소 수정)
라이브에서 "피부 주름을 완전히 없애 주는 앰플"이 걸리지 않고 "피부 재생"만 걸렸다. 광고 문구 사전/510 hard-claims에서 "주름 + 없애/제거/완전히" 조합이 왜 빠지는지 원인을 보고서에 쓰고, 기존 규칙 근거(의약품 오인·효능 과장) 안에서 패턴을 보강한다. 새 규칙 ID를 만들지 말고 기존 규칙의 패턴/사전에 추가, 회귀 케이스 5개 이상(걸려야 하는 것 3, 걸리면 안 되는 것 2: 예 "주름 개선에 도움"(기능성 인정 문구), "메이크업을 완전히 지워 주는").
