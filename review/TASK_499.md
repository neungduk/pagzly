# 499차 — 큰 PDF 지원: 브라우저에서 글자만 추출해 전송 (PDF 파일은 서버로 보내지 않음)

## 0. 규칙
- 유료 호출 금지. Production·main 금지. 코드 삭제 금지(기존 서버 업로드 경로 유지). 규칙 데이터 수정 금지. "위반" 단정·"완벽/보장" 금지.
- **먼저** `node_modules/next/dist/docs/`에서 클라이언트 번들·워커·동적 import 관련 안내를 읽고, 이 Next 버전에서 pdfjs 워커 로딩이 가능한 방식을 `499-targets.md`에 기재한 뒤 구현(AGENTS.md 지침).
- 새 의존성은 `pdfjs-dist` 하나만 허용(이미 간접 의존 중인 버전과 맞출 것). 번들 크기 증가를 보고서에 기재. 클라 추출 코드는 `/label-check` 계열 페이지에서만 **동적 import**(다른 페이지 번들에 포함 금지).
- 마무리 전 `npx tsc --noEmit`, `npm run build`. 커밋 최대 4개. 보고서 `review/499cha-report.md`.

## 1. 목표
498차에서 업로드 한도를 4MB로 낮췄다. 실제 인쇄용 PDF는 대부분 이보다 크다. 사용자의 **브라우저에서** PDF를 열어 텍스트 조각(문자열·글자 크기·쪽 번호)만 추출하고 그 JSON만 서버로 보낸다. PDF 원본은 서버로 가지 않는다("저장하지 않음" 약속과 일치).

## 2. 설계
- 공통 타입 `ExtractedLabelPayload`(서버 `ExtractedPdf`와 같은 의미): `{ pageCount, pages:[{page, items:[{text,sizePt}]}], emptyPages }`. 서버는 기존 점검 함수에 이 구조를 입력으로 받는 진입점을 추가(`runLabelCheckFromExtracted`). 기존 `runLabelCheck483(buffer)`는 그대로 유지하고 내부에서 같은 점검 코어를 공유하도록 최소 리팩터링.
- 클라이언트: 파일이 4MB 이하이면 기존 서버 업로드(현행) 유지가 아니라 **항상 클라 추출을 우선 시도**하고, 실패(워커 로딩 실패·브라우저 미지원) 시 4MB 이하 파일에 한해 기존 경로로 폴백. 4MB 초과 + 클라 추출 실패 → 지금의 큰 파일 안내.
- 한도 상수: 클라이언트 파일 상한 **100MB**(상수, 메모리 보호), 쪽수 상한 현행(10) 유지. 전송 JSON 상한 상수(예: 300KB)와 서버 검증(항목 수·문자열 길이 상한, 타입 검사, 총 글자 수 상한). 초과 시 `TOO_LARGE` 안내.
- 서버는 JSON 입력을 **신뢰하지 않는다**: 스키마 검증 실패 → `UNREADABLE`/`BAD_REQUEST`. 이 점검기는 사용자 본인 파일을 사전 점검하는 도구이므로 위조 방지는 목표가 아니나, 서버 폭주 방지(길이·개수 상한)는 필수.
- 진행 표시: "내 컴퓨터에서 글자를 읽는 중" 한 줄 외 새 카피 금지(원본 파일이 서버로 가지 않는다는 점은 이미 있는 면책 구조 안에서만 표현, 단정적 보안 문구 금지: "안전합니다" 사용 금지).
- 이미지 PDF(글자 없음) 판정은 클라에서도 동일하게(0자 → 기존 이미지 PDF 안내).
- 로그인 사용자의 결과 요약 저장(495)·수정 제안·시장 선택은 새 경로에서도 동일하게 동작해야 한다.

## 3. 시험
- 서버 진입점 `runLabelCheckFromExtracted` 단위 회귀: 기존 시안(A·B·C, i1~i6, us1~us4)에서 서버가 추출한 구조를 JSON으로 직렬화한 뒤 새 진입점에 넣어 **기존 결과와 동일**함을 확인(`label-check-499.ts`).
- 스키마 검증 시험(과대 항목 수·너무 긴 문자열·타입 오류·음수 크기).
- 클라 추출은 Node 환경에서 pdfjs 레거시 빌드로 같은 코드를 호출하는 시험을 시도하고, 불가하면 "브라우저 실측 미실시"를 맨 위에 기재.
- 기존 회귀 전부 유지.
